# マイログ(mylog.sapp.jp)仕様書

版 0.35(2026-10-29)

この文書は、アプリの外から見た仕様(テキスト記法、計画との照合、要確認、ビュー、画面、画面からの編集、保存)を定める。実装の作り方は、計算部の取り込み(12 章)を除いて定めない。実装は index.html(単一 HTML)で、この仕様書に沿って作る。

## 1 章 目的と範囲

### 1.1 目的

プロジェクトの実行中に、各人が日々の作業(タスク・時間・状態・進捗率)、問題と依頼、テストの結果・TRL・TPM を、1 つのテキストに書き足していく。プロジェクト計画(plan.sapp.jp)の `.plan` と照合して名前の誤りを見つけ、記録の形から詰まりの兆候を示す。

価値の中心は、工数の把握ではなく、問題が起きていないか(詰まっていないか、依頼が放置されていないか)を拾い出すことにある。

画面は、計画の中の自分(自分の担当のタスクの過去・現在・未来と、その進み具合)を中心に見せる。記録は、それを書き込む手段である。

プロジェクトの実行中は、次の流れで使う。

1. 各人がマイログ(このアプリ)に書く。
2. プロジェクト分析(projalysis.sapp.jp)の作業分析で全員のマイログを集め、計画への反映候補と要確認を見る。
3. 決めた変更を、利用者がプロジェクト計画で `.plan` に書く。

### 1.2 範囲

- 1 人 1 ファイルとし、プロジェクトの期間を通して同じファイルに書き足す。
- 計画書(`.plan`・`.plans`)は読むだけで、書き換えない。計画への反映は、利用者がプロジェクト計画で行う。
- 複数人のマイログの集計と、他人のマイログにある返事との突き合わせは扱わない(プロジェクト分析の作業分析で行う)。
- 課題管理の詳しい内容(原因・影響度・優先度・対策・期限)、AI 利用状況、次回計画の文章は扱わない(アプリの外で書く)。
- 進捗率は本人の主観の値として扱う。見積もりと日程の計算には使わず、止まっていることの検知(6 章)にだけ使う。
- 追記(過去の日付の記録を後から足したこと)を見つける機能は持たない。`version:` で最後に保存した日を残すだけとする。
- 使う人と使い方は定めない。
- プロジェクト計画の計画書を読んで使う。計画書がなくても記録は書けるが、名前の照合・担当のタスク・計画を使う兆候・今週の予定・計画の変更は出ない。どのアプリをどう組み合わせるかは定めない(プロジェクトを運営する人が決める)。README と書き方に、ほかのアプリとの関係と、マイログを使う組み合わせの例を書く。

### 1.3 S Apps としての前提

- 単一 HTML で、サーバーにデータを送らず、ネットなしで動く。
- 外部ライブラリを読み込まない。
- アプリ本体に Node.js を含めない。ビルドと検査に使うのはよい。
- 同じテキストと同じ計画書の一覧からは、必ず同じ表と図を出す(決定的)。ただし、要確認(6 章)と、今日より後の日付の警告(3.4 節)だけは、表示する日の日付で変わる。
- ライセンスは MIT とする。

### 1.4 名前

- アプリ名(上の帯・タブの題名): マイログ
- 公開先: mylog.sapp.jp
- リポジトリ名: mylog

## 2 章 用語

| 用語 | 意味 |
|---|---|
| マイログ | このアプリで書くテキスト。拡張子は `.mylog` |

| 日付の行 | 字下げなしの `- YYYY-MM-DD` の行(3.4 節) |

| 計画書の一覧 | 読み込んだ計画書の並び(5 章) |

| 合計時間 | 記録先の `hours:` の合計(7.3 節) |
| 記録日数 | 週のまとめで、その週に記録の行のある日の数(7.7 節) |

## 3 章 テキスト記法

### 3.1 全体の形

```
version: 2026-04-30
by: 青木
week: wed

- 2026-04-27
  - 通知用APIの実装 hours: 3 status: doing progress: 40 ask: 井上 note: メール送信の設定を相談した
- 2026-04-28
  - 通知用APIの実装 hours: 3 status: blocked issue: SMTP の認証が通らない
  - 登録確認メール test: ng mop: 予定の登録から 1 分以内にメールが届く
  - 登録確認メール trl: 2
```

- 階層は `-` の字下げだけで作る。プロジェクト計画と同じく、Markdown に由来するのはこの部分だけで、それ以外は独自の記法である。
- 文字コードは UTF-8 とする。改行は LF と CRLF のどちらも読む。

### 3.2 行の種類

注(3.9 節)を取り除いた後、各行は次のどれか 1 つでなければならない。どれにも当たらない行は構文エラーとする。

1. **空行**: 空白とタブだけの行も含む。全角の空白だけの行も空行とする(字下げではないので害がない)。どこに置いてもよい。
2. **設定の行**: 字下げなしで、予約語の `version`・`by`・`week` に `:` が続く行。
3. **日付の行**: 字下げなしで `- ` が続く行。
4. **記録の行**: 字下げ(1 個以上の空白・タブ)の後に `- ` が続く行。

`- ` は、ハイフンと半角の空白またはタブ 1 個以上とする。ハイフンの後が全角の空白なら構文エラーとする。字下げに全角の空白を使った行も構文エラーとする(プロジェクト計画と同じ)。

### 3.3 設定の行

| 設定 | 値 | 必須 |
|---|---|---|
| `version:` | 日付 1 つ | 省略可 |
| `by:` | 名前 1 つ(このマイログの記録者) | 必須 |
| `week:` | 曜日 1 つ(`mon`〜`sun`) | 省略可。省略したら `mon` とする |

- `version:` は 1 行目にだけ、字下げせずに書ける。ほかの場所の `version:` は構文エラーとする(プロジェクト計画の仕様書 3.3 節と同じ)。
- `by:`・`week:` を書く場所は自由である(日付の行の間でもよい)。各 1 回だけ書ける。2 回書いたら構文エラーとする。
- `by:` がなければエラーとする。

### 3.4 日付の行と記録の行

- 日付の行の名前は `YYYY-MM-DD` の日付とする。日付でない名前、実在しない日付は構文エラーとする。
- 日付の行に書ける属性は `note:` だけとする。
- 記録の行は、その前にあるいちばん近い日付の行に属する。日付の行より前にある記録の行は構文エラーとする。
- 記録の行は子を持たない。字下げの深さが違う記録の行も、すべて同じ日付の行の記録とする(字下げの幅をそろえなくてよい)。
- 日付の行の下に記録の行がなくてもよい。
- 日付の行が、前の日付の行より前の日付なら警告とする。同じ日付の行が 2 つ以上あれば警告とし、どちらの記録も使う。
- 日付の行が今日より後の日付なら警告とする。次回計画はマイログの外で書くため。
- 記録の行どうしは、同じ名前が何度出てもよい(1 行が 1 つの記録のため)。

### 3.5 値の書き方

**名前**

- 記録の行では、`- ` の後ろから、最初の「空白 + 属性の予約語 + `:`」の手前までを名前とする。前後の空白は除く。名前は空にできない。
- 名前には空白を含めてよい。`,` は含められない。`::` は修飾(3.7 節)にだけ使える。
- 名前の大文字と小文字、全角と半角は区別する(プロジェクト計画と同じ)。

**時間**

- `hours:` の値は 0 より大きい 10 進数とし、小数を書ける。小数点以下は 2 桁までとする。24 を超える値は構文エラーとする。

**進捗率**

- `progress:` の値は 0 以上 100 以下の整数(百分率)とする。`%` は付けない。

**TRL**

- `trl:` の値は 0 以上の整数とする。段階の数(4 段階・9 段階など)は検査しない。

**状態**

- `status:` の値は `todo`・`doing`・`done`・`blocked` のどれかとする(プロジェクト計画と同じ)。

**結果**

- `test:`・`reviewed:` の値は `ok` か `ng` とする。大文字と小文字は区別する。

**名前の並び**

- `review:`・`ask:` の値は、人の名前をカンマで区切って並べる。各名前の前後の空白は除く。同じ名前を 2 回書いたら警告とし、1 回とみなす。

**曜日**

- `mon`・`tue`・`wed`・`thu`・`fri`・`sat`・`sun` の 7 つである(プロジェクト計画と同じ)。

**自由な文**

- `issue:`・`solved:`・`answered:`・`tpm:`・`mop:`・`note:` の値は自由な文で、カンマで区切らない。値は、次の「空白 + 属性の予約語 + `:`」の手前、または行末までとする。

### 3.6 属性

属性は記録の行に書く(`note:` は日付の行にも書ける)。

| 属性 | 値 | 種類 | 意味(4 章) |
|---|---|---|---|
| `hours:` | 時間 | タスク | その日にかけた時間 |
| `status:` | 状態 | タスク | その日の時点の状態 |
| `progress:` | 進捗率 | タスク | その日の時点の進捗率(主観) |
| `review:` | 名前の並び | タスク | 確認を依頼した相手 |
| `reviewed:` | `ok`・`ng` | タスク | 確認した結果 |
| `trl:` | TRL | 機能 | その日の時点の TRL |
| `tpm:` | 自由な文 | 機能 | その日に測った TPM の値(数と単位) |
| `test:` | `ok`・`ng` | 機能 | テストの結果。`mop:` と組で書く |
| `mop:` | 自由な文 | 機能 | テストした MOP の文。`test:` と組で書く |
| `issue:` | 自由な文 | 中立 | 起きている問題 |
| `solved:` | 自由な文 | 中立 | 問題が解決したことの記録 |
| `ask:` | 名前の並び | 中立 | 質問した相手 |
| `answered:` | 自由な文 | 中立 | 受けた質問に答えたことの記録(答えの要旨) |
| `note:` | 自由な文 | 中立 | メモ |

- 「種類」は、記録先を探す範囲を決める(3.7 節)。
- 同じ属性を同じ行に 2 回書いたら構文エラーとする。
- 「タスク」の属性と「機能」の属性を同じ行に書いたら構文エラーとする。
- `test:` と `mop:` は同じ行に組で書く。片方だけなら構文エラーとする。
- 予約語は小文字とし、大文字と小文字は区別する。
- `help:` は書けない(チームの外の人に助けを求める記録は扱わない。人に聞くのは、チームの人への `ask:` だけとする)。書いたら構文エラーとし、`ask:` を使うよう診断に示す。日付の行や、名前のない記録の行に書いたときも同じく示す。
- 属性を書く順は自由である。属性のない記録の行(名前だけの行)は警告とする。

### 3.7 記録先

記録の名前は、照合する版(5.4 節)の要素を指す。計画書の一覧が空のときは照合せず、名前のまま扱う。

**探す範囲**

| 記録の行の属性 | 探す範囲 |
|---|---|
| 「タスク」の属性がある | WBS の要素(根を除く) |
| 「機能」の属性がある | FBS の要素(根を含む) |
| 「中立」の属性だけ | WBS の要素(根を除く)を探し、なければ FBS の要素(根を含む)を探す |

**決め方**

- 名前の探し方は、プロジェクト計画の仕様書 3.7 節と同じとする。範囲の中に名前が 1 つだけあれば、それを指す。`親::子` の修飾名は、その並びが要素の祖先の並びの末尾と一致する要素を指す。
- 1 つもなければ、警告する(ただし、最新の版で 1 つに決まる名前には出さない。5.6 節)。記録は名前のまま使う(集計では「計画にない作業」として扱う。後の版で計画に足したときと、計画に足した後に削除したときの扱いは 5.6 節)。
- 2 つ以上あれば、曖昧な名前として警告し、候補を示す。記録は計画にない作業と同じに扱う。
- 照合は、プロジェクト計画と違ってエラーにしない。計画書はマイログと別のファイルで、途中で変わるため。

**記録先による警告**

- `status:`・`progress:` の記録先がタスク(WBS の末端)でなければ警告とし、その属性を無視する。`hours:`・`review:`・`reviewed:` は途中の要素にも書ける(その要素の作業として扱う)。
- `test:` の `mop:` の文が、記録先の FBS の要素の MOP(`mop:` か `mop*:`)のどれとも 1 文字も違わずに一致しなければ警告とする。前後の空白は比べない。
- `by:` の名前が、最新の版(5.4 節)の `members:` にいなければ警告とする(`by:` の行には日付がなく、照合する版が決まらないため)。`review:`・`ask:` の名前は、その記録の照合する版の `members:` で調べる。

### 3.8 照合の対象にしない記録

- 計画書の一覧が空のとき、記録先を決めず、3.7 節の警告を出さない。
- 照合に使える版がない日付(5.4 節)の記録も同じとする。

### 3.9 注

- `//` から行末までを注として読み飛ばす。`//` が注になるのは、行頭か、直前が空白・タブの場合だけとする(プロジェクト計画と同じ)。

### 3.10 構文エラーにするもの

プロジェクト計画の仕様書 3.9 節と同じく、上の規則に合わない行はすべて構文エラーとし、とくに次のものは専用の診断文を出す。

| 書き方 | 判定 |
|---|---|
| 見出し | 字下げの後が `#` で始まる行 |
| 番号付きのリスト | 字下げの後が「数字 + `.` または `)` + 空白」で始まる行 |
| `*`・`+` のリスト | 字下げの後が `* `・`+ ` で始まる行 |
| 太字 | 名前、または自由に書く文の属性(`note:`・`mop:`・`issue:`・`solved:`・`answered:`・`tpm:`)以外の値に `**` か `__` を含む |
| 説明の文 | 3.2 節のどれにも当たらない行 |
| コードブロック | 字下げの後が ```` ``` ```` で始まる行 |

- 自由に書く文の属性の値には `**`・`__` を書ける(`__init__.py` を直す、など)。文字のまま表示し、太字にはしない。プロジェクト計画の仕様書 3.9 節と同じ考え方で、`mop:` の値はプロジェクト計画でも書けるので、照合はそのまま成り立つ。

## 4 章 予約語の意味

### 4.1 設定

- `version:` は、最後にファイルとして保存した日である。保存のときにアプリが書く(9 章)。表・図・兆候には使わない。
- `by:` は、このマイログの記録者である。その名前は、このファイルのすべての記録の行に受け継がれる。
- `week:` は、週の始まりの曜日である。週ごとの表(7 章)の区切りに使う。

### 4.2 作業の記録

- `hours:` は、その日にその記録先にかけた時間である。同じ日の同じ記録先の時間は足し合わせる。1 日の `hours:` の合計が 24 を超えたら警告とする。
- `status:` は、その日の時点のタスクの状態である。値と画面の表示は、プロジェクト計画と同じ(実行前・実行中・完了・問題発生)とする。記録の行に書かなければ、その日の状態は報告していないとする(実行前とはみなさない)。ただし、`status:` を書かずに `progress:` を書いた行は、進捗率から状態を決める(100 なら完了、100 未満なら実行中)。
- `progress:` は、その日の時点の進捗率(本人の主観)である。書かなければ、その日の進捗率は報告していないとする。
- 同じタスクの、最も新しい日付の報告(同じ日付なら、テキストで後ろの行)を「最後の報告」とする。状態と進捗率は、それぞれ別に最後の報告を取る。
- プロジェクト分析で、同じタスクを複数の人が報告しているとき(作業を分担しているとき)は、人ごとの最後の報告をとってからまとめる。マイログの一覧の順にはよらない。マイログ(1 人分)では、その人の最後の報告そのものになる。
  - 状態: 全員の最後の状態が完了なら完了。1 人でも問題発生なら問題発生。それ以外で、誰かが実行中か完了なら実行中。それ以外は実行前。
  - 進捗率: 人ごとの最後の進捗率の平均(整数に丸める)。片方が 0、片方が 100 なら 50 とする(完了に見えないように)。
  - まとめるのは、最新の版(5.4 節。プロジェクト分析では基準日の版)でそのタスクの作成者(`by:`)になっている人の報告だけとする。ただし、作成者の誰も報告していなければ、報告した全員でまとめる。作成者を交代したとき、外れた人の古い報告が残らないようにするため。日ごとのまとめ(問題の続き・手戻り・進捗の停止)も同じとし、作成者の誰かが一度でもその値を報告していれば、すべての日で作成者の報告だけを使う(外れた人の古い報告で、手戻りや問題の続きが出ないように)。
- `status:` と `progress:` の食い違いは警告とする。
  - 同じ行で `status: done` なのに `progress:` が 100 でない。
  - 同じ行で `progress: 100` なのに `status:` が `done` でない(`status:` を書いていないときを除く)。

### 4.3 問題と依頼

- `issue:` は、記録先で起きている問題である。同じ記録先か同じ名前(書いたままの名前)の、それより後の `solved:` が書かれるまで、未解決とする。同じ名前でも閉じるのは、計画の変更で名前が一意でなくなったり、名前が変わったりした後にも、前に書いた名前で閉じられるようにするためである。
- 「それより後」は、日付が後か、同じ日付でテキストで後ろの行とする。`issue:` と同じ行の `solved:` では閉じない(画面から解決を記録するときは、別の行に書く。11.5 節)。プロジェクト分析では、同じ日付の別の人のマイログの `solved:` も、行の順によらず後とみなす(プロジェクト分析の仕様書 6.3 節)。
- `status: blocked` も、`issue:` がなくても未解決とする。同じタスクに、それより後で `blocked` 以外の状態が報告されるか、`issue:` と同じ規則で `solved:` が書かれるまで続く。`solved:` の後に、また `blocked` が報告されたら、その日から未解決とする。
- プロジェクト分析で、同じタスクを複数の人が報告しているときは、日ごとに、その日までの人ごとの最後の報告でまとめた状態(4.2 節)で見る。まとめた状態が問題発生になった日の `blocked` を未解決の始まりとし、まとめた状態が問題発生でなくなるか、`solved:` が書かれるまで続く。閉じ方は、マイログの一覧の順によらない。
- 同じ記録先の `issue:` と `blocked` は、それぞれ別に未解決かを決める。同じ行に書いた `issue:` と `status: blocked` だけは、1 件の問題として数える(未解決の問題の表と S2 に 2 回出さない)。
- `review:` は、記録先の確認を名前の人に依頼したことである。依頼された人が、自分のマイログで同じ記録先か同じ名前(書いたままの名前)に `reviewed:` を書くと、対応したとする(突き合わせはプロジェクト分析で行う)。
- `reviewed:` は、確認した結果である。`ng` は差し戻しを意味する。
- `ask:` は、記録先について名前の人に質問したことである。質問された人が、自分のマイログで同じ記録先か同じ名前に `answered:` を書くと、対応したとする(突き合わせはプロジェクト分析で行う)。
- `answered:` は、質問に答えたことである。値は答えの要旨とする。
- マイログは自分のファイルしか持たないので、依頼に返事があったかは分からない。マイログでは「出した依頼」として一覧にするだけとする(6.3 節)。

### 4.4 テスト・TRL・TPM

- `test:` は、`mop:` の文の MOP をテストした結果である。テストした日は日付の行の日付とする。
- `trl:` は、記録先の機能の、その日の時点の TRL である。
- 最後のテストの結果と、週の最後の TRL は、いちばん新しい日付の記録とする。プロジェクト分析で同じ日付に別の人の記録があるときは、一覧の順によらず、テストは `ng` を、TRL は小さい方をとる(低い方に倒す)。
- `tpm:` は、記録先の機能の、その日に測った TPM の値である。アプリは中身を解釈しない(数として計算しない)。

### 4.5 `note:`

- 記録や日付についてのメモである。表・兆候には使わない。

## 5 章 計画書の一覧

計画書(`.plan`・`.plans`)の扱いは、プロジェクト分析(projalysis.sapp.jp)の仕様書 3 章と同じとする。違う点は、一覧をファイルに保存しないことだけである。

### 5.1 読めるファイル

- `.plan`: プロジェクト計画のテキスト。
- `.plans`: プロジェクト分析で保存した plans。中のマイログ(`logs`)は読まない(開いているマイログを置き換えないため。本人の `.mylog` を正本とする)。読まなかったことを、計画書の一覧に知らせる。
- `.txt`: プロジェクト計画が、ファイル操作機能のないブラウザで保存した計画書。`.plan` と同じに読む。
- `.svg`: プロジェクト計画の版 0.30 までに保存した画像。中の計画を 1 つの版として読む(プロジェクト分析の仕様書 3.1 節と同じ)。
- 計画書は読むだけで、書き換えない。

### 5.2 計算部

- `.plan` は、プロジェクト計画の計算部(core.js の `/*CORE-BEGIN*/` 〜 `/*CORE-END*/`)の `analyze` で読む(12 章)。
- 記録先の探し方(3.7 節)は、計算部の外に置く。規則はプロジェクト計画の仕様書 3.7 節と同じにする。

### 5.3 足す・並び・版の名前

プロジェクト分析の仕様書 3.3 節〜3.6 節と同じとする。

- 開く・ファイルを置くは、どちらも一覧に足す。`.plans` を足したときは、その中の `.plan` をすべて足す。
- テキストが一覧のどれかと 1 文字も違わない `.plan` は足さず、その旨を知らせる。`version:` の日付だけが違うものは、別の版として足す。
- 各版に外すボタンを付ける。
- 版の日付の古い順に並べる。同じ日付の中は足した順とし、同じ日付の中だけ上へ(▲)・下へ(▼)のボタンで並べ替えられる。
- `.plans` を足したときは、同じ日付の版の並びを、plans の中の並びに合わせる(一覧にすでにある版も。プロジェクト分析で並べ替えた結果を引き継ぐため)。
- 版の名前は「YYYY-MM-DD 版」「YYYY-MM-DD 版 (2)」…とする。
- エラーのある版と `version:` のない版は、一覧に並べてその旨を示し、照合には使わない。

### 5.4 照合する版

- 日付の行ごとに、照合に使える版(エラーがなく、版の日付がある版)のうち、版の日付がその日付以前のもので、一覧でいちばん後ろの版を、照合する版とする。
- その日付以前の版がなければ、照合に使える版のうち一覧でいちばん前の版とする。
- 版の日付と同じ日付の記録は、計画を直す前に前の名前で書いたものがありうる。その版で名前が 1 つの要素に決まらなければ、同じ日付のそれより上の版を下から順に、続いてそれより前の日付の最後の版を探し、最初に 1 つの要素に決まった版で照合する。どの版でも決まらなければ、はじめの版で照合し、診断を出す。`status:`・`progress:` のある記録が、その版で途中の要素に当たるとき(その日にタスクを分けたとき)も同じく前の版を探し、タスクに当たった版で照合する(見つからなければ、はじめの版で照合し、途中の要素の `status:`・`progress:` は無視する)。
- 照合に使える版がなければ、照合しない(3.8 節)。計画書の一覧に版があるのに照合に使える版がないときは、診断欄にその旨を 1 件だけ出す。
- 兆候(6 章)で計画を使うもの(作成者・日数・終了予定日・確認者)は、照合に使える版のうち、版の日付が今日以前で一覧でいちばん後ろの版(最新の版)を使う。今日より後の日付の版があれば、最新の版としては使わず、診断欄にその旨を 1 件出す。

### 5.5 名前が変わったとき

- 記録は書いた日の計画の名前で書かれ、後から書き直さない前提とする。
- 名前が変わった版の日付より前の日付の記録は古い版で、版の日付以降の記録は新しい版で照合される(5.4 節)。古い記録が、計画にない作業になることはない。版の日付と同じ日付に前の名前で書いた記録は、前の版でも探す(5.4 節)。
- 集計(7 章)では、記録先を対応名(根を除いた祖先と自分の名前を `::` でつないだもの。プロジェクト分析の仕様書 4.1 節)で分ける。記録先は 5.6 節の規則で最新の版の要素に寄せる。名前が変わった記録先は寄せず、別の行になる(推測して対応づけない)。
- 表の「タスク」「記録先」「機能」の列には、対応名を書く(列名には「(対応名)」を付けない)。

### 5.6 版をまたいだ記録先

計画は、最初の版からどんどん変わる。記録した日の版で照合した記録先を、最新の版の要素に寄せ、計画が変わった後も、前の記録を今のタスクの記録として数えられるようにする。境界は、プロジェクト分析の計画書分析の対応づけ(プロジェクト分析の仕様書 4 章)と同じとし、推測はしない。

- 集計・兆候・表(6 章・7 章)と画面からの編集(11 章)では、記録先を最新の版の要素に寄せる。プロジェクト分析では、基準日の版の要素に寄せる(プロジェクト分析の仕様書 3.8 節)。
- 計画にあった記録先は、記録した日の照合する版(5.4 節)から寄せる先の版まで、一覧で隣り合う版ごとに、プロジェクト分析の仕様書 4 章の対応(4.1 節の対応名、4.2 節の根、4.3 節の移動)でたどる。最後までたどれれば、寄せる先の版の要素を記録先とする。移動したタスクの記録は、移動の後のタスクの記録になる。
- たどれない記録先は、記録した日の照合する版の記録先のままとする。名前を変えた要素(プロジェクト分析の仕様書 4.4 節。推測しない)と、移動の候補に同じ名前が 2 つ以上ある要素(4.3 節)が当たる。これらは、今の計画のタスクとは別の行になる。
- 計画にない作業だった記録は、寄せる先の版で、書いた名前を 3.7 節の探し方で探す。ちょうど 1 つの要素に決まれば、その要素を記録先とする(計画にない作業を、後の版で計画に足したとき)。
- 寄せる先の版にない記録先のうち、記録した日の版で計画にあったもの(名前を変えた・削除した要素)と、記録した日の照合する版から寄せる先の版までのどれかの版で名前が 1 つに決まったもの(計画に足した後に削除した作業。削除した後に初めて書いた記録は、計画にない作業のままとする。寄せる先の版で名前が 2 つ以上あるときは除き、曖昧な名前のままとする)は「計画から削除」の記録先とする。記録した日の版の対応名と同じ要素が寄せる先の版にあれば、計画から削除とはしない。表では、名前の後ろに「(計画から削除)」と書く(計画にない作業の「(計画にない作業)」の代わり)。計画に足した後に削除した作業の記録は、名前が 1 つに決まった最後の版の要素を記録先とする(書き方が違っても、同じ要素なら 1 行にまとめる)。
- 照合の診断(10 章)は、記録した日の照合する版で出す。寄せた後の記録先では出し直さない。ただし、記録した日の版にない名前でも、最新の版で 1 つの要素に決まる名前(後の版で計画に足した作業)には、名前がないという診断を出さない(直す必要がないため)。診断の文は「…にありません(この日の版にない名前です)」とし、その後の扱い(計画にない作業か、計画から削除か)は言わない(後の版で変わるため)。

## 6 章 要確認

マイログでは、自分のマイログと計画だけで分かる兆候を示す。他人のマイログが要る兆候(依頼の返事の待ち)は、プロジェクト分析の作業分析で示す。

### 6.1 今日

- 兆候の日数は今日までで数える。今日は、表示する日の日付とする。表示したまま日付が変わったら描き直す(プロジェクト計画のガントチャートと同じ)。

### 6.2 兆候

兆候は、規則と、それに当たった記録の行だけを示す。良し悪しの判断や解釈の文は出さない。

| 番号 | 兆候 | 規則 | 計画が要るか | 既定の値 |
|---|---|---|---|---|
| S1 | 記録の途絶 | 最新の版で `by:` に自分が入っているタスクのうち、最後の報告(なければ計画の `status:`)が完了でないものがあり、今日までの N 日の間に記録の行が 1 つもない。プロジェクトの開始日(`start:`)が今日より後なら判定しない | 要る | 7 日 |
| S2 | 問題の長期化 | 未解決(4.3 節)の `issue:`・`blocked` が、最初の日から今日まで N 日以上続いている | 要らない | 7 日 |
| S4 | 日数の超過 | あるタスクで、作業日数(`hours:` を書いた日の数)が、最新の版の `days:` を超えたのに、最後の報告が完了でない | 要る | ― |
| S5 | 終了予定日の超過 | 最新の版の担当を入れた日程(プロジェクト計画の仕様書 6.3 節)でのタスクの終了予定日から、今日まで N 日以上たち、最後の報告(なければ計画の `status:`)が完了でない | 要る | 1 日 |
| S6 | 手戻り | 日ごとの状態(4.2 節のまとめ方)が、完了から実行中か問題発生に戻った | 要らない | ― |
| S7 | 計画にない作業 | ある週の `hours:` の合計のうち、計画にない作業の時間が N % 以上 | 要る | 50 % |
| S8 | 進捗の停止 | あるタスクの進捗率(4.2 節のまとめ方)が、N 日以上前から変わっていない。最後の報告が完了か、進捗率が 100 のものは除く。計画があるときは、最新の版のタスク(5.6 節で寄せた記録先)と、計画にない作業の記録先だけを見る(名前を変える前の記録先や、途中の要素になった記録先には出さない) | 要らない | 14 日 |
| S9 | 確認の抜け | 最新の版で、作成者以外の確認者(`review:`。受け継いだものを含む)がいるタスクを完了と報告したのに、それ以前(同じ日を含む)にそのタスクへの `review:` の記録がない | 要る | ― |

- 番号は、プロジェクト分析の仕様書 6.3 節と共通にする(S3 はプロジェクト分析だけの兆候「返事待ち」)。
- 計画が要る兆候は、計画書の一覧が空のとき判定しない。サマリーのビューの要確認に「計画書を読み込むと判定する兆候: S1・S4・S5・S7・S9」と示す。
- 規則の値(N)は、設定のダイアログで変えられる。変えた値は自動保持に残す(マイログのファイルには書かない)。
- S7 は週(4.1 節)ごとに判定する。今日を含む週は、今日までの分で判定する。

### 6.3 出した依頼

- 自分が書いた `review:`・`ask:` を、日付・種類(確認・質問)・相手・記録先の表で示す。
- 返事があったかは示さない(プロジェクト分析で突き合わせる)。

## 7 章 ビュー

ビューは、計画の中の自分(自分の担当のタスクの過去・現在・未来と、その進み具合)を中心にする。並びは次のとおりとする。

| 順 | ビュー | 内容 |
|---|---|---|
| 1 | サマリー | 今日の時点の自分の状況のまとめ(7.2 節) |
| 2 | タスク | 自分の担当のタスクを、区分(7.1 節)ごとに分けた表(7.3 節) |
| 3 | ガントチャート | 自分の担当のタスクを計画の日程で描き、記録した日に印を付けた図(7.4 節) |
| 4 | 週のまとめ | 選んだ週の記録を 1 枚にまとめた表(7.7 節) |
| 5 | 作業時間 | 週ごとの作業時間の表と図、記録のカレンダー(7.5 節) |
| 6 | テスト・TRL・TPM | 担当するテスト項目、テストの記録・TRL の推移・TPM の推移の表(7.6 節) |

- 表は SVG で描く(画像の保存と印刷のため)。図の色は黒とし、強調にだけ色(えんじ)を使う。状態の色は、プロジェクト計画のガントチャートと同じとする。
- 表の行を押すと、テキストの該当する記録の行を選び、編集パネルを出す(11 章)。記録のないタスクの行は、11.4 節の「今日の記録」の欄だけを出す。

### 7.1 担当のタスク(用語)

- 担当のタスク: 最新の版で、`by:` に自分(`by:` の設定の名前)が入っているタスク(受け継いだ `by:` を含む)。
- 確認するタスク: 最新の版で、`review:` に自分が入り、`by:` に自分が入っていないタスク。
- 今の状態: そのタスクの最後の報告(4.2 節)の状態。報告がなければ、最新の版の `status:`(なければ実行前)。画面では「今の進捗」と表示する。
- 最後の状態: そのタスクの最後の報告の状態(報告だけを見る。報告がなければ「―」)。画面では「最後の進捗」と表示する。
- 計画の状態: 最新の版の `status:`(なければ実行前)。画面では「計画の進捗」と表示する。
- 確認待ち: 今の状態が完了でなく、そのタスクの最後の `review:`(確認の依頼)が最後の状態の報告と同じ行かそれより後にあるもの。今の進捗の欄に「実行中(確認待ち)」のように、今の状態の後ろに添えて出す(状態の値は増やさない。区分は今の状態で決める)。依頼の後に状態を報告するか、完了と報告すると終わる。マイログは相手の返事を見られないので、返事があったかは見ない。プロジェクト分析では、依頼した相手の全員が、依頼の日以降にそのタスクに確認の結果(`reviewed:`)を書いていれば終わる。
- 始めた日: そのタスクに初めて `hours:` を書いた日と、初めて実行中・完了・問題発生を報告した日のうち、早い方。`note:` などだけの記録は数えない。どちらもなければ「―」。
- 開始予定日・終了予定日: 最新の版の担当を入れた日程(プロジェクト計画の仕様書 6.3 節)での、そのタスクの最初の日と最後の日。
- 予定の期間: 開始予定日から終了予定日まで。表では「MM-DD〜MM-DD」、1 日だけなら「MM-DD」と書く(プロジェクト分析と同じ)。
- 区分: 担当のタスクを、次の順に判定して、どれか 1 つの区分に入れる(1 つのタスクが 2 つの表に出ないように)。
  1. 遅延: 終了予定日が今日より前で、今の状態が完了でない。
  2. 問題発生: 今の状態が問題発生。
  3. 開始予定日を過ぎた未着手: 今の状態が実行前で、開始予定日が今日か今日より前。
  4. 実行中: 今の状態が実行中。
  5. 開始予定日がまだ先: 今の状態が実行前で、開始予定日が今日より後。
  6. 完了: 今の状態が完了。
- 区分の表は、次の順に並べる。対応が要る区分(遅延・問題発生・開始予定日を過ぎた未着手)の表を、ほかの区分の表と混ぜずに続けて置く。
  1. 実行中のタスク
  2. 遅延のタスク
  3. 問題発生のタスク
  4. 開始予定日を過ぎた未着手のタスク
  5. 開始予定日がまだ先のタスク
  6. 完了したタスク

### 7.2 サマリー

上から次のものを並べる。

1. 状況: 今日の日付、照合した計画書の最新の版の名前、担当のタスクの件数(区分ごと)。
2. タスクの区分: 区分ごとの件数を 1 つの表にまとめる。行は 7.1 節の区分を 7.1 節の順に並べ、列は「区分・件数・日数・タスク(WBS 番号)」とする。日数は、その区分のタスクの計画の `days:` の合計とする。タスク(WBS 番号)は、その区分のタスクの WBS の管理番号を開始予定日の順に並べ、遅延の区分では番号の後ろに遅延の日数を添える(例: 「2.2.3(1 日)」)。完了の区分は番号を書かない。タスクの詳しい内容(名前・予定の期間・状態など)は、タスクのビュー(7.3 節)で見る。
3. 今週の予定: 担当のタスクのうち、予定の期間(開始予定日から終了予定日まで)が今週(今日を含む週。週の始まりは `week:`)に 1 日でもかかるもの。列は「WBS 番号・タスク・予定の期間・今週の日・今の進捗」とし、今週の日は、予定の期間のうち今週の日の範囲(「MM-DD〜MM-DD」、1 日なら「MM-DD」)とする。行の並びは 7.3 節と同じとする。該当がなければ「なし」とする。終了予定日を過ぎて終わっていないタスク(遅延)は、予定の期間が今週にかからなければ入れない(遅延は 2. の表と要確認の S5 で示す)。
4. 計画の変更: 計画書の一覧の照合に使える版(5.4 節)のうち、最後の版(最新の版)と、それより前の日付の最後の版を比べ、自分に関係する変更を表にする。同じ日付に何回保存しても、その日の途中の版とは比べない。前の日付の版がなければ、1 つ前の版と比べる。題に比べた 2 つの版の名前(5.3 節)を書く。タスクは 5.6 節の対応(対応名と移動)で対応させる。列は「変更・タスク・内容」とし、変更は次の 6 種類とする。
   - 作成者の追加: 最新の版で `by:` に自分がいて、前の版ではいない(前の版にないタスクも含む)。内容は「作成者: 前の作成者 → 今の作成者」、前の版にないタスクは「計画に追加(予定の期間、日数)」。
   - 作成者の削除: 前の版で `by:` に自分がいて、最新の版ではいない(最新の版にないタスクも含む)。内容は「作成者: 前の作成者 → 今の作成者」か「計画から削除」。
   - 日程の変更: 両方の版で `by:` に自分がいて、予定の期間か `days:` が違う。内容は「前の予定の期間 → 今の予定の期間」とし、`days:` が違うときは「(日数 前 → 今)」を添える。予定の期間は、それぞれの版の担当を入れた日程による(ほかの人の担当が変わったために日程がずれたタスクも出る)。最新の版で完了のタスクは出さない(完了のタスクは版の日付より前に置かれうるので、日程が前へ詰まっても計画の変更ではないため。プロジェクト計画の仕様書 6.3 節)。
   - 確認者の追加・確認者の削除: `review:` について、作成者の追加・削除と同じ。内容は「確認者: 前 → 今」か「計画に追加(作成者: …)」「計画から削除」。
   - 移動: 自分が作成者か確認者のタスクの親が変わった(5.6 節で対応した移動)。内容は「親: 前の親の対応名 → 今の親の対応名」(親が根なら「(根)」)。移動したタスクを、削除と追加の 2 行にはしない。
   - どちらかの版でタスク(末端の要素)でなくなっても、要素としては残っているとき(子を足して途中の要素になった、など)は、その要素の `by:`・`review:`(受け継いだものを含む)で比べ、「計画から削除」「計画に追加」とはしない。
   - 行の並びは、変更の種類を上の順に並べ、同じ種類の中は最新の版(削除は前の版)の WBS の木の順とする。照合に使える版が 1 つだけのときは「比べられません」と、変更がないときは「作成者・確認者・日程の変更はありません」と示す。
5. 未解決の問題: 未解決(4.3 節)の `issue:`・`blocked` すべての表(日数によらない)。列は「記録先・内容・日付・日数」とする。
6. 要確認: 6.2 節の兆候の表。列は「兆候・記録先・内容・日付」とし、内容は規則に当たった事実(日数・時間・値)を書く。例: 「未解決 9 日(2026-04-28 から): 予定登録APIの仕様が決まらず、テストケースを作れない」(S2 は問題の文を添える)。兆候がなければ「兆候はありません」とする。表の上に、今日の日付と規則の値を書く(画像だけを保存しても、どの日の判定かがわかるように)。表の画像にも、表の上にこの 1 行を入れる。今日より後の日付の記録は、5. の未解決の問題と兆候に数えない。
7. 出した依頼: 6.3 節の表。
8. 確認するタスク: 列は「タスク・作成者・終了予定日・計画の進捗・確認の結果」とする。確認の結果は、そのタスクに自分が書いた最後の `reviewed:` とする。

- 計画書の一覧が空のときは、1.〜4. と 8. の代わりに「計画書を追加すると、担当のタスクが出ます」と示す。計画書の一覧に版があるのに照合に使える版がないときは、代わりに「計画書の一覧に、照合に使える版がありません」と示す(タスクのビュー・テストのビューの同じ知らせも同じ)。

### 7.3 タスク

- 7.1 節の区分の表(6 つ)を、7.1 節の順に並べる。表の中の行の並びは、開始予定日の順、同じなら WBS の木の順とする。
- 列は「WBS 番号・タスク・予定の期間・始めた日・日数・作業日数・計画の進捗・今の進捗・進捗率・合計時間・最後の記録」とする。始めた日は 7.1 節のとおり(予定の期間と並べ、前倒しで始めたか、遅れて始めたかを見るため)。WBS 番号は WBS の管理番号(プロジェクト計画の仕様書 7.1 節)、予定の期間は「MM-DD〜MM-DD」(1 日だけなら「MM-DD」。7.1 節)、日数は計画の `days:`、作業日数は自分が `hours:` を書いた日の数(要確認の S4 と同じ数え方。1 日も書いていなければ「―」。予定の日数と実際にかけた日数を見比べるため)、計画の進捗は最新の版の `status:`、今の進捗は今の状態を状態の色で塗り、進捗率は最後の報告、合計時間は自分の `hours:` の合計、最後の記録はそのタスクの最後の記録の日付とする。記録のないタスクは「記録なし」と書く。遅延が発生しているタスクの表には「遅延」(終了予定日から今日までの日数)の列を足す。
- 続いて「確認するタスク」の表(7.2 節の 8. と同じ)を置く。
- 続いて「担当外の記録」の表を置く。担当のタスクでも確認するタスクでもない記録先(他人のタスク・FBS の機能・計画にない作業)ごとに 1 行とし、列を「記録先・合計時間・作業日数・最初の日・最後の日・最後の進捗・最後の進捗率」とする。計画にない作業は、名前の後ろに「(計画にない作業)」と書く(計画から削除した記録先は「(計画から削除)」。5.6 節)。行の並びは、最新の版の WBS の木の順、続いて FBS の木の順、最後に計画にない作業を最初に書いた順とする。
- 計画書の一覧が空のときは、記録先ごとのまとめの表(担当外の記録と同じ列)だけを置き、「計画書を追加すると、担当のタスクが出ます」と示す。

### 7.4 ガントチャート

- 行は担当のタスク(開始予定日の順、同じなら WBS の木の順)とし、左に管理番号とタスクの名前を置く。名前が入りきらないときは名前の先頭を「…」で省く(管理番号は省かない)。行の文字にマウスを置くと、管理番号と名前の全文を出す。
- 棒は、開始予定日から終了予定日までを描き、今の状態の色で塗る(プロジェクト計画のガントチャートと同じ色)。休みの日で棒を切らない。
- 自分が `hours:` を書いた日に、その行の棒の下に黒い点を打つ(予定と実際に作業した日を見比べるため)。
- 今日の縦線を引く。遅延が発生しているタスクは、棒の右上にえんじの丸を付ける(プロジェクト計画の担当者別ガントチャートと同じ)。
- 目盛りは月・日の 2 段とする。図の期間は、担当のタスクの最初の開始予定日(と、担当のタスクに `hours:` を書いた最初の日の早い方。担当外の記録は入れない)から、最後の終了予定日と今日の遅い方までとする。期間が 1096 日を超えるときは描かずに、その旨を示す(プロジェクト計画と同じ)。
- 計画書の一覧が空のとき、担当のタスクがないときは、その旨を示す。

### 7.5 作業時間

- 行を記録先、列を週とする表に、`hours:` の合計を書く。最後の行に週ごとの合計を置く。
- 列の見出しは週の始まりの日付(「MM-DD〜」)とする。列は、`hours:` を書いた最初の週から最後の週までとする。
- 表の下に、週ごとの合計時間の棒の図を置く。
- 続いて「記録のカレンダー」の図を置く。
  - 行を週(週の始まりは `week:`)、列を曜日とし、1 日を 1 つのます目にする。ます目の左上に「M/D」、右下にその日の `hours:` の合計を書く。時間を書かずに記録だけある日は「記録」と書く。
  - ます目は、その日の時間で塗る(0 は白、2 時間未満・2 時間以上・5 時間以上の 3 段の灰色)。今日のます目は、えんじの太い枠で囲む。
  - 期間は、最初の記録の週(今日の方が早ければ今日の週)から、最後の記録の週と今日の週の遅い方までとする。156 週(1092 日)を超えるときは描かずに、その旨を示す。
  - `hours:` の記録が 1 つもないときは、作業時間のビュー全体と同じく「hours: の記録がありません」とだけ示す。

### 7.6 テスト・TRL・TPM

- 担当するテスト項目: ビューの先頭に置く。
  - 担当のタスクの `for:`(受け継いだものを含む)の PBS の要素が `realizes:` で実現する機能(FBS の要素)を集め、その機能の MOP を 1 行ずつ並べる(最新の版による)。
  - 列は「機能・MOP・計画・最後のテスト・関係するタスク」とする。計画は、計画でチェック済み(`mop*:`)なら「✓」とする。最後のテストは、このマイログでその機能に書いた `test:` のうち、`mop:` の文がその MOP と一致する最後の記録の結果と日付(「ok(2026-04-29)」)とし、なければ「未実施」とする。関係するタスクは、その機能にたどり着いた担当のタスクの管理番号とする。
  - 行の並びは FBS の木の順、同じ機能の中は MOP を書いた順とする。MOP のない機能は「(MOP なし)」の 1 行とする。
  - 最後のテストのある行を押すと、その `test:` の記録の行を選ぶ(11.2 節)。
  - 計画書の一覧が空のときは「計画書を追加すると、担当のタスクが出ます」と示す。該当する機能がないときは「なし」とする。
- テストの記録: 列を「日付・機能・MOP・結果・メモ」とする。同じ MOP の 2 回目からのテストには、結果の前に「再」と書く。
- TRL の推移: 行を機能、列を週とし、その週の最後の報告の値を書く。報告のない週は空とする。
- TPM の推移: TRL と同じ形で、書いたままの文を書く。

### 7.7 週のまとめ

選んだ 1 週間の記録を 1 枚にまとめる(週ごとの振り返りや、週報の材料にするため)。

- 週は、ビューの上の帯の選択欄で選ぶ(8 章)。選べる週は、最初の記録の週と今日の週の早い方から、最後の記録の週と今日の週の遅い方まで(記録のない週も含む)とし、記録には日付の行だけの日(日付の行のメモだけの日)も含める。選べる週は新しい順に並べる。既定は今週(今日を含む週)とする。選んだ週は保存しない(開き直したら今週に戻る)。印刷(9 章)では今週を出す。週を変えたら、記録の編集パネル(11.2 節)を閉じる(選んでいた記録が表に出なくなることがあるため)。
- 題は「週のまとめ(YYYY-MM-DD〜YYYY-MM-DD)」とし、その下に、名前(`by:`)、記録日数(その週の記録の行のある日の数。日付の行だけの日は数えない)、合計時間を書く。
- 続いて次の表を置く。どれも、該当がなければ「なし」とする。行を押すと、その記録の行を選ぶ(11.2 節)。
  1. この週の作業時間: 列は「記録先・時間・日」。記録先の並びは 7.3 節(担当外の記録)と同じ。日は `hours:` を書いた日(「MM-DD」をつなげる)。
  2. この週の報告: `status:` か `progress:` のある記録。列は「日付・記録先・進捗・進捗率」。
  3. この週の問題と解決: `issue:`(種類「問題」)と `solved:`(種類「解決」)。列は「日付・記録先・種類・内容」。
  4. この週の依頼と返事: `review:`(確認の依頼)・`ask:`(質問)は相手ごとに 1 行、`reviewed:`(確認の結果)・`answered:`(回答)は 1 行。列は「日付」「種類」「相手・内容」「記録先」の 4 列とし、「相手・内容」には、依頼は相手の名前、返事は結果(ok・ng)か回答の要旨を書く。
  5. この週のメモ: 記録の行の `note:` と、日付の行の `note:`(記録先は「(日付の行)」)。列は「日付・記録先・メモ」。
  6. この週のテスト・TRL・TPM: `test:`(「テスト ok: MOP の文」)・`trl:`・`tpm:`。列は「日付・機能・内容」。
- 表の中の行は、日付の順とし、同じ日付の中はテキストに書いた順とする(日付の行を逆の順に書いても、日付の順になる)。

## 8 章 画面

画面の構成と配色・字体は、プロジェクト計画に合わせる。

- **上の帯**: 新規、開く、上書き保存、別名で保存、印刷 / PDF、ファイル名、ビューの選択欄、記録を追加、AI で記録(11.6 節)、計画書を追加、設定、例を読み込む、書き方。保存したことの表示と、自動保持(9 章)の警告もここに出す。
- **左**:
  - 色付きのテキスト欄。予約語と日付の行を色付けする。
  - その下に診断欄(10 章)。
  - その下に計画書の一覧(5 章)。各版に、版の名前・ファイル名・警告の件数またはエラー・並べ替えのボタン・外すボタンを示す。一覧は折りたためる。
- **右**: ビューと、その下の編集パネル(11 章)。週のまとめ(7.7 節)のときだけ、ビューの上に週を選ぶ帯(「週のまとめで見る週」の選択欄。選択肢は「MM-DD〜」、今週には「(今週)」を添える)を出す。
- **仕組み**:
  - 左右の分割バー
  - ドラッグ・アンド・ドロップでの読み込み(9 章)
  - 「書き方」のダイアログ(枠外のクリックで閉じる)
  - 「設定」のダイアログ(6.2 節の規則の値。枠外のクリックで閉じる)
  - フッター
- テキスト欄で Tab キーを押すと、空白 2 個を入れる(プロジェクト計画と同じ)。
- 名前の補完: テキスト欄で記録の行の名前を書いているとき、その日付の照合する版のタスク名・機能名から、書いた文字を含むものを候補として出す。マイログの行に書けない名前・MOP の文(「空白 + 予約語 + `:`」か「空白 + `//`」を含むもの)は候補に出さず、記録を追加の欄にその名前を知らせる。`mop:` の値を書いているときは、その行の記録先の MOP の文を候補として出す。候補を選ぶと、テキストに入れる(一意に決まるいちばん短い修飾名)。計画書の一覧が空のときは出さない。
- 例を読み込む: 付録 A のマイログを開き、計画書の一覧を付録 A の計画書の 2 つの版だけに入れ替える(計画書の一覧に計画書があるときは、入れ替えてよいかを確かめる。計画書のファイルは消えない)。
  - 例は 2026-04-29 を今日とみなして作ってある。読み込むときは、マイログと計画のすべての日付(`version:`・`start:`・`end:`・日付の行など)を同じ日数だけずらし、読み込んだ日が 2026-04-29 に当たるようにする。ずらす日数が 7 の倍数でないと曜日が変わって週の区切りがずれるので、`week:` の曜日も同じ日数だけずらす(例の水曜始まりの週が、読み込んだ日の曜日に合わせて変わる)。これにより、いつ読み込んでも、今日がプロジェクトの途中になり、7.1 節の区分の表と、7.2 節の今週の予定・計画の変更、7.5 節の記録のカレンダー、7.6 節の担当するテスト項目、7.7 節の週のまとめ(今週)の表がすべて埋まる。

## 9 章 保存と読み込み

保存と読み込みは、プロジェクト計画の仕様書 9 章に合わせる。違う点は次のとおり。

- テキストの拡張子は `.mylog` とする。
- 別名で保存の名前の候補は、`by:` の名前に `.mylog` を付けたもの(例: `青木.mylog`)とする。`by:` がないかエラーのときは、今のファイル名、なければ `mylog.mylog` とする。
- `version:` の扱いは、プロジェクト計画の仕様書 9 章と同じとする(内容が同じなら版も同じ。上書き保存・別名で保存のときに、内容が変わっていれば今日の日付にする。1 行目にだけ書ける)。
- 開く(ファイル選択)・ファイルを置くでは、ファイルの種類で次のように扱う。
  - `.mylog`: テキストとして開く(今のテキストを入れ替える)。保存していない変更があれば、破棄してよいかを確かめる。
  - `.plan`・`.txt`・`.plans`・`.svg`: 計画書の一覧に足す(5 章)。テキストは変えない。`.plans` の中のマイログは読まない(5.1 節)。
  - 一度に置いたファイルに `.mylog` が 2 つ以上あれば、`.mylog` は開かずに「マイログは 1 つずつ開いてください」と知らせる(`.plan`・`.plans` は足す)。
  - 開けない拡張子のファイルは、開けないことを知らせて読まない。
- 図・表の保存(コピー・SVG・PNG・PDF)と印刷 / PDF は、プロジェクト計画の仕様書 9 章と同じとする。ファイル名は「元の名前_ビューの識別子_図の識別子か表の題」とする(プロジェクト計画の仕様書 9 章と同じ形)。ビューの識別子は、サマリー `summary`、タスク `mytasks`、ガントチャート `gantt`、週のまとめ `week`、作業時間 `hours`、テスト・TRL・TPM `tests` とする。図の識別子は、ガントチャートの図 `gantt`、作業時間の「週ごとの合計時間」の図 `weekly`、「記録のカレンダー」の図 `calendar` とする。表の題は表の上の題(「担当外の記録」など)とする。例: `青木_gantt_gantt.svg`、`青木_mytasks_担当外の記録.svg`。元の名前と表の題は、ファイル名に使えない文字と空白を「_」にする。
  - 要確認の表には、題に今日の日付を入れる(例: 「要確認(2026-05-06)」)。
- 自動保持: 編集中のテキスト・ファイル名・保存していない変更があるか・`version:` の比べる相手・計画書の一覧(各版のファイル名とテキスト、並び)・6.2 節の規則の値・表示中のビューを、変わるたびに、このブラウザの `localStorage` に保持する。どこにも送信しない。
  - 開いたときは、保持してある内容を続きとして開く。なければ空で開く。
  - 保持に失敗したとき、別のタブで同じマイログが変わったときは、上の帯に警告を出す(プロジェクト計画と同じ)。
- 計画書の一覧は、ファイルに保存しない。

## 10 章 診断

- 診断はエラーと警告の 2 段階とする(プロジェクト計画と同じ)。
  - エラーは、構文エラーと、必須の `by:` がないことだけとする。エラーがあるときは、表と図と兆候を計算しない。エラーの間は、最後に正しく計算できた表を薄く表示する。
  - 計画との照合の結果(3.7 節)は、すべて警告とする。
- 件数の要約を出す。
- 項目ごと(構文・必須・日付・書き方・計画との照合・値の食い違い)の一覧を出し、押すと該当箇所を選ぶ。
- 各診断に行を付ける。
- 兆候(6 章)は診断に入れない(サマリーのビューで示す)。

## 11 章 画面からの編集

### 11.1 原則

- テキストが正本である。画面での操作は、すべてテキストの書き換えとして行い、画面の側にはデータを持たない(プロジェクト計画の仕様書 11.1 節と同じ)。
- 書き換えた直後に、待たずにテキストを解析し直して描き直す。
- テキストにエラーがある間(表が薄い間)と、テキストを打った後で描き直しが済んでいない間は、画面から編集できない。
- 1 回の操作は、テキスト欄の 1 回の書き換えとして行い、テキスト欄で Ctrl+Z 1 回で元に戻せる。
- 書き込む前に、書き換えたテキストを解析し直し、次をすべて満たすときだけ書き込む。満たさないときは、テキストを変えずに理由を編集パネルに出す。
  1. エラーが出ない。
  2. 操作の対象でない記録の行は、日付・名前・属性が変わらない。
  3. 操作の対象は、意図したとおりになる(書いた値がそのまま属性の値として読める、足した記録が意図した日付の記録になる、など)。
- 記録は履歴なので、ある記録の行を直す操作(11.2 節)と、今日の記録を足す操作(11.3 節〜11.5 節)を分ける。

### 11.2 記録の編集パネル

- 表の行のうち記録の行に結び付いたものを押すと、テキストのその記録の行を選び、ビューの下の編集パネルに、その記録の日付と名前と属性をテキストのとおりに出す。
- 欄は、名前と、3.6 節の属性すべてとする。`status:` は空と 4 択(「実行前(todo)」など。プロジェクト計画と同じ表記)、`test:`・`reviewed:` は空と `ok`・`ng` の選択欄とし、選ぶとすぐ書き込む。
- 欄を書き換えて Enter を押すと(または欄から離れると)、その記録の行に書き込む。欄を空にすると、その属性を消す。Escape で書きかけをやめる。日本語入力の変換中の Enter では書き込まない。
- 書き換えた行は、字下げ・名前・属性(書いてあった順。新しい属性は後ろに足す)・注を、この順につなぎ直す。属性の間の空白は 1 個にそろう。
- 「この記録を消す」で、記録の行を消す(消す前に確認を出す)。日付の行は、記録がなくなっても残す。
- 名前を変えても、ほかの記録の行の名前は変えない(記録の行は 1 行ずつ独立しているため)。
- ビューの表の行のほか(何もないところ)を押すと、選択を外し、編集パネルを閉じる(プロジェクト計画と同じ)。記録を追加の欄(11.3 節)を開いているときも閉じる。週のまとめの週を選ぶ帯(7.7 節)の、選択欄のほかの所を押したときも閉じる。
- テキストにエラーがある間に表の行を押すと、編集パネルに「画面から編集できません」と「テキストのエラーを直すと、画面から編集できます」を出す。記録を選んでいる間にテキストがエラーになったときも同じとし、エラーを直すと選んでいた記録の欄に戻る。
- 欄の書き込みは、Enter と欄から離れることが続けて起きても 1 回だけとする(Ctrl+Z 1 回で戻るように。11.1 節)。
- 選んでいる記録は、行の番号と行の文で追う。テキストに行を足したり消したりして番号がずれても、同じ文の行(いちばん近いもの)を選び続ける。同じ文の行がなくなれば、編集パネルを閉じる(別の記録を書き換えないため)。

### 11.3 記録を追加のパネル

- 上の帯の「記録を追加」で、編集パネルに記録を追加する欄を出す。
- 欄は、日付(既定は今日)、名前(その日付の照合する版のタスク・機能から選べる。書いてもよい)、時間、進捗、進捗率、確認の依頼の相手(`review:`)、問題(`issue:`)、質問の相手(`ask:`)、メモとする。名前が機能のときは、確認の依頼の相手と問題の間に、テストの結果・MOP(その機能の MOP から選ぶ)・TRL・TPM の欄も出す。
- 「追加」を押すと、その日付の日付の行(2 つ以上あれば最後のもの)の記録の最後に、記録の行を足す。字下げは、その日付の行のほかの記録の行と同じ、なければ空白 2 個とする。
- その日付の日付の行がなければ、日付の行も足す。場所は、日付の並びが崩れないよう、それより後の日付の行のうち最初のものの前、なければテキストの最後とする。
- 足した後は、足した記録の行を選ぶ。日付と名前の欄は残し、ほかの欄は空にする。
- 「記録を追加」を押して欄を開くたびに、日付は今日に戻す(名前と、書きかけのほかの欄は残す)。新規・開く・例を読み込むなどでテキストを入れ替えたときは、すべての欄を空にする。
- 名前を書いてすぐ「追加」を押したときも、1 回で足す。名前が機能になって機能の欄を出すときは、欄を出し直してから足す。

### 11.4 担当のタスクからの更新

- タスクのビューの区分の表(7.1 節)の行を押すと、編集パネルの先頭に「今日の記録」の欄(進捗の 4 択、進捗率、時間)を出し、その下に 11.2 節の欄(その記録先の最後の記録。記録がなければ出さない)を出す。
- 「今日の記録」の欄で書き込むと、過去の記録の行は変えず、今日の記録に書く。今日の記録の行のうち、同じ記録先の行(書いた名前によらない)を見る。
  - 欄には、同じ記録先の行のうち、その属性を持つ最後の行の値を出す。
  - 書き込むと、その値を出した行の属性を書き換える。その属性を持つ行がなければ、同じ記録先の最後の行に書き足す。同じ記録先の行がなければ、11.3 節と同じ規則で記録の行を足す。
- 足す行の名前は、今日に使う版(5.4 節)で、その記録先の一意に決まる(WBS と FBS の両方で)いちばん短い修飾名とする。計画にない記録先なら、その記録先の最後の記録の行の名前とする(前に書いた名前が、計画の変更で一意でなくなったり、変わったりしても、同じ記録先に書けるようにするため)。
- 足した行が別の記録先になるときは、書き込まずに「同じ記録先に書けませんでした」と知らせる。ただし、記録先が今日に使う版にないとき(名前を変える前の記録先など。5.6 節)は、書いたままの名前で足す。その行は計画にない作業として照合されるが、同じ名前の規則(4.3 節)で問題が閉じる。
- 進捗率・時間の欄を空にして書き込むと、値を出した行から、その属性を消す(11.2 節の欄と同じ)。その属性を持つ行がなければ、書き込まずに「今日の記録に progress: がないので、消すものはありません」のように知らせる。

### 11.5 未解決の問題からの操作

- サマリーの「未解決の問題」の行と、要確認の S2(問題の長期化)の行を押すと、編集パネルの先頭に「解決を記録」の欄(解決の内容と「記録する」のボタン)を出し、その下に 11.2 節の欄を出す。
- 「記録する」は、今日の記録の、同じ記録先の最後の行に `solved: 解決の内容` を書く。同じ記録先の行がないときは、11.4 節と同じ名前で、11.3 節と同じ規則で記録の行を足す。解決の内容は空にできない。ただし、書き込む先の行に `issue:` か `status: blocked` があるときは、その行には書かずに、記録の行を足す(同じ行の `solved:` では問題が閉じないため。4.3 節)。
- 記録した後は、「解決を記録」の欄を閉じ、書き込んだ記録の行の 11.2 節の欄だけを出す(続けて「記録する」を押して、前の `solved:` を書き換えないため)。

### 11.6 AI で記録

今日の記録を、生成 AI に質問してもらいながら書くための機能である。アプリは AI に何も送信しない。生成 AI に貼るプロンプト(指示の文)をクリップボードにコピーするだけで、AI に貼ること、AI が出した記録を確かめること、テキストに貼ることは、本人が行う。AI が出した記録が正しいかを本人に確かめさせることを、この機能の要とする。

- 上の帯の「記録を追加」の右に「AI で記録」のボタンを置く。ボタンを押しても、すぐにはコピーしない。編集パネルに次のものを出す(押すたびに手順が目に入り、ボタンを押すと AI が記録してくれると思われないようにするため)。
  - 題「AI で今日の記録を書く」と、「このアプリは AI に何も送信しません。次の手順で、自分で AI に貼ってください。」の文、「閉じる」のボタン。
  - 手順: 1. 「プロンプトをコピー」を押す。2. 使っている生成 AI(ChatGPT・Gemini・Claude など)に貼る。3. AI の質問に答える。最後に出る記録の案を、自分で確かめる(違っていたら AI に直させる)。4. 正しければ、AI が出した行を左のテキストの最後に貼る。
  - 「プロンプトをコピー」のボタン。押すとクリップボードにコピーし、ボタンの文字を 2 秒だけ「コピーしました」にする(表の「コピー」と同じ)。テキストにエラーがあるときは押せず、「テキストのエラーを直すと使えます」と示す。
  - 名前の置き換えの対応(「名前の置き換え: メンバーA = 井上、…(AI が出した行を貼った後に、本当の名前に直す)」)。置き換えた名前がなければ「なし」とする。対応は画面に出すだけで、プロンプトには入れない。
- テキストは変えない(ほかの編集パネルと違い、テキストを書き換えない)。パネルは、ほかの編集パネルと同じく、ビューの何もないところを押すと閉じる。
- プロンプトは次の 3 つからなる。今日は、表示する日の日付とする。
  1. 進め方: 本人に 1〜2 問ずつ質問すること、尋ねること(作業したタスクと時間、状態と進捗率、問題、解決、依頼、頼まれた確認の結果や答えたこと、テスト)、時間・進捗率・状態・結果は本人の答えのとおりに書き推測で埋めないこと、質問が終わったら記録の行の案とその内容を日本語の文で言い直したものを見せて「この内容で正しいですか。直すところはありますか」と尋ねること、本人が正しいと答えるまで繰り返し、正しいと答えたら今日の分の行だけを 1 つのコードブロックで出すこと、伏せた名前をそのまま使うこと。
  2. 書き方: 日付の行と記録の行の形、名前は「書ける名前」から 1 文字も変えずに選ぶこと(一覧にない作業は本人に名前を確かめる)、属性の意味と値の書き方(4 章)、タスクの属性と機能の属性を同じ行に書かないこと、見出し・番号付きのリスト・説明の文の行を書かないこと、`**`・`__` は名前と名前を書く値に書かないこと(自由に書く文の値には書ける。3.10 節)、`test:` と `mop:` を組で書くこと。今日の日付の行がすでにあるときは、日付の行は出さずに記録の行だけを出し、今日すでに書いた記録と同じ内容は出し直さないこと。
  3. 今日の状況: 今日の日付、担当のタスクのうち完了以外のもの(名前・予定の期間・区分・今の状態(文では「今の進捗」)・進捗率・最後の記録の日)、確認するタスクのうちまだ ok の結果を書いていないもの、担当するテスト項目(7.6 節。機能の名前・MOP の文・最後のテスト)、未解決の問題(7.2 節)、書ける名前(完了以外の担当のタスク・確認するタスク・担当するテスト項目の機能。どれも一意に決まるいちばん短い修飾名)、記録のある最後の 3 日(今日を除く。日付の新しい方から 3 つの日付で、日付の順に並べる。同じ日付の行が 2 つあれば両方)の記録の行、今日すでに書いた記録の行。計画書の一覧が空のときは、担当のタスクがわからないことを書き、計画から作る項目を省く。
- 人の名前を伏せる。
  - 自分(`by:` の名前)は「本人」と書く。
  - 計画の照合に使える版のどれかの `members:` にいる人と、記録の `review:`・`ask:` に書いた相手は、プロンプトの文の中に最初に出る順に「メンバーA」「メンバーB」…(Z の次は AA)と書く。
  - 置き換えは、3. の今日の状況のうち、マイログと計画から取った中身(注・`note:`・`issue:` などの自由な文を含む)に対して行う。進め方・書き方・見出しなどの決まった文は置き換えない。中身の値と同じ行にある決まった語(「予定」「最後のテスト」など)も置き換えない(人の名前が「テスト」などの言葉と同じでも、指示の文を崩さないため)。
  - 長い名前から先に置き換える(短い名前が長い名前の一部のときに崩さないため)。長い名前の一部としてしか出ていない短い名前は、記号を振らず、名前の置き換えの対応にも出さない。
  - 限界: `members:` にも依頼の相手にもない名前(あだ名・先生の名前など)を自由な文に書いていても、見分けられないので伏せられない。タスク名・機能名に人の名前が入っているときは、名前の一部が置き換わる。
  - AI が出した行の「メンバーA」などは、貼った後に本人が本当の名前に直す。直し忘れた `review:`・`ask:` の相手は、`members:` にいない名前として警告される(3.7 節)。
- AI が出した行は、普通に書いた記録と同じく、照合と診断(10 章)を受ける。名前の誤りや書き方の誤りは、診断で見つかる。

  - 3.7 節の記録先の決め方(修飾名、計画にない作業、曖昧な名前、MOP の文の一致)と、5.4 節の照合する版の選び方(名前が変わった前後の記録)。
  - 4.2 節・4.3 節の最後の報告、未解決の判定(同じ日付の別の人の報告が、一覧の順によらないこと。計算が終わること)。
  - 5.6 節の版をまたいだ記録先(移動はたどる、名前の変更はたどらない、同じ名前が 2 つ以上なら移動にしない、計画にない作業を後の版の要素にする、寄せる先を替えると寄せ直す)。プロジェクト分析の計画書分析の対応づけと同じ対応になること(隣のプロジェクト分析のリポジトリ ../projalysis があるときだけ行う。プロジェクト分析の検査でも同じことを確かめる)。

  - 11.6 節の AI で記録(プロンプトに人の名前が入らないこと、名前の置き換えの順と長い名前の扱い、今日の記録の有無による書き方の違い、計画がないとき)。
  - 6.2 節の兆候の判定(今日を固定して)。S1・S4・S5・S8 は、出る日と出ない日の境い目を含める。
  - 同じテキストと計画書の一覧から同じ SVG を描くこと(今日を固定して)。
  - 付録 A の例を、いくつかの日に日付をずらして読み込み、診断が出ず、7.1 節の区分の表とサマリーの表、週のまとめ・記録のカレンダー・担当するテスト項目がすべて埋まること。
